4주차 · 변경 이력을 남기며 협업하기 실습

실습 전에

혼자 관리하던 코드를 공개했더니, 처음 보는 사용자가 실행 안내를 고쳐 주겠다고 합니다. 변경은 받아보고 싶지만 기본 버전을 직접 바꿀 권한까지 주지는 않으려 합니다.

01 변경 내용을 남기는 이유

실행 안내를 고친 뒤 문제가 생겼다면, 무엇을 바꿨는지 어떻게 확인할 수 있을까요?

설명
  • 변경 내용을 설명과 함께 이력으로 남기는 작업을 Commit이라고 합니다.
  • 수정 전후 내용을 비교하면 빠진 준비 단계를 어디에 추가했는지, 다른 설명까지 바뀌었는지 확인할 수 있습니다.

02 여러 사람이 작업하는 방법

직접 수정 권한을 주지 않으면서도 다른 사람의 개선을 받아들이려면, 어떤 과정이 필요할까요?

설명
  • 기여자가 자신의 사본에서 변경을 만들고, 원본에 반영해 달라는 Pull Request(PR)를 보냅니다. 관리자는 변경 내용과 이유를 먼저 확인할 수 있습니다.
  • 필요한 수정을 함께 검토한 뒤 관리자가 Merge하면 원본에 반영됩니다. 변경을 제안할 기회와 기본 버전을 바꿀 권한을 분리하는 방식입니다.
실습 안내로 이동 ↓

한 사이클로 보기: 외부 사용자가 실행 안내를 개선한다면

혼자 작업한다면 main에서 직접 수정하고 Commit으로 이력을 남길 수 있습니다. 작은 팀에서 작업을 충분히 조율할 수 있다면, 친구를 Collaborator로 초대해 저장소 수정 권한을 공유하고 직접 반영하는 방식도 가능합니다. 항상 별도의 검토 요청을 거쳐야 하는 것은 아닙니다.

그런데 처음 보는 사람이 “설명을 고쳐 드릴게요”라고 제안한다면 어떨까요? 제안은 받아보고 싶지만, 기본 버전을 바로 바꿀 권한까지 줄 필요는 없습니다. 이때 자신의 사본에서 수정한 내용을 제안하고, 관리자가 검토한 뒤 반영하는 흐름이 유용합니다. 서로 아는 팀이라도 여러 사람이 사용하는 기본 버전에는 같은 검토 절차를 둘 수 있습니다.

공개된 실습 코드를 처음 사용하다가 README에 실행 준비 단계가 빠진 것을 발견했습니다. 나는 이 저장소를 직접 수정할 권한이 없지만, 안내를 보완해 관리자에게 제안하려고 합니다.

필수 실습은 이 흐름을 단순화해 본인 Repository에서 Branch·Commit·PR·Merge를 경험합니다. 본인이 수정자와 검토자의 역할을 모두 맡으므로 Fork는 필요하지 않습니다. 시간이 남으면 동료 Repository를 Fork해 원본에 PR을 제안하는 과정까지 연결합니다.

이번 실습의 두 작업 공간: Colab의 임시 Repository에서는 수정·Commit·Branch를 연습합니다. 이어서 GitHub에 별도의 연습 Repository를 만들어 웹에서 PR과 Merge까지 진행합니다. Colab의 예제가 GitHub에 자동으로 올라가는 것은 아닙니다.

로컬에서 작업할 때 Push는 어디에 들어가나요?

컴퓨터나 Colab에서 만든 Commit을 GitHub에도 보내려면 Push가 필요합니다. 즉, 로컬에서 수정·Commit한 뒤 Push하고, GitHub에서 PR을 만듭니다. 이번 GitHub 단계처럼 웹에서 직접 수정·Commit한 내용은 이미 GitHub에 기록되어 있으므로 별도의 로컬 Push가 필요하지 않습니다.

학습자료에서 전체 흐름과 단계별 설명 보기 ↗

아래 필수 활동을 약 60분 동안 수행하며, 막히는 부분은 조교의 도움을 받으세요.

진행 순서

  1. Colab에서 파일 수정·Commit·Branch를 연습합니다.
  2. GitHub에서 연습 Repository를 만들고, practice Branch의 변경을 PR로 검토한 뒤 main에 Merge합니다.
  3. 파일 수정·Commit·PR·Merge 이력을 정리합니다.
  4. 실행 환경을 다시 시작하고 위에서부터 실행해 결과가 다시 나오는지 확인한 뒤 저장합니다.

1. 내 작업 공간에서 Git 연습하기

① 로컬 예제의 문장을 한 줄 수정하고 git diff→add→commit→log를 직접 반복하세요. ② GitHub에서 README를 포함한 개인 연습 Repository를 만드세요. ③ 새 Branch practice를 만들고 README에 이번 주 배운 내용을 추가하여 Commit하세요. ④ practice→main의 Pull Request를 열고 Files changed에서 변경을 검토한 뒤 Merge하세요. ⑤ 조교 또는 동료에게 두 Branch의 역할과 Merge 전후 차이를 설명하세요. ⑥ Repository URL, Commit 이력, PR 변경 내용과 Merge 완료 화면을 Notebook에 기록하세요. 40분 안에 마치면 선택: 동료의 연습 Repository를 Fork하고 한 줄 수정하여 원본으로 PR을 제안해 Collaborator 방식과 비교하세요.

제출·저장

수정한 내용, Commit·Pull Request·Merge 이력, 각 단계에서 한 일을 설명한 메모를 포함하세요. 기준 예제만 실행한 파일은 직접 수행 항목을 완료한 것이 아닙니다. 제출은 KLAS를 이용하며 기한은 학기 일정과 최신 공지를 확인합니다.

GitHub 협업 결과는 저장소·Branch·PR의 변경 내용과 Merge 이력이 보이는 캡처로 남기세요. 인증 정보는 포함하지 않습니다. Notebook은 연습·기록용입니다.

선택 실습

시간이 남으면 동료의 연습 Repository를 Fork하고 문장 한 줄을 수정해 Pull Request를 제안하세요. 본인 Repository에서 Branch를 만드는 방식과 비교하세요. 추가 활동은 필수 60분 실습을 완료한 뒤 진행합니다.
